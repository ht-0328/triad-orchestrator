# 運用手順

## 標準の操作方法

人間の標準入口はVS CodeのCodexまたはClaude Code拡張チャット、あるいはAntigravity CLIである。人間は実現したいこと、承認、修正理由、判断だけを自然言語で伝える。Triad CLI、Git、Docker Composeの定型操作はチャット担当AIがオーケストレーターとして実行し、人間へシェルコマンドの入力を求めない。

成果物を作成するAI、独立レビューを行うAI、チャットの窓口を担当するAIは別の概念である。Claude Codeのチャットを開いていても、Codex担当フェーズはCLI経由でCodexへ割り当てる。チャット担当が別担当の成果物を代筆してはならない。

## リポジトリの配置

本基盤と対象アプリケーションは別のGitリポジトリにする。

```text
<workspace>/
├── triad-orchestrator/
└── application-repository/
```

新しいアプリケーションを作る最初の依頼では、VS Codeで`triad-orchestrator`を開く。既存アプリケーションへ導入するときは、本基盤と対象リポジトリが同じVS Codeワークスペースから見える状態が望ましい。初期化後は対象リポジトリに`AGENTS.md`、`CLAUDE.md`、`GEMINI.md`、`.ai-dev/chat-interface.md`が追加されるため、以後は対象リポジトリだけを開いて会話を継続できる。

対象リポジトリのルートはGitで解決する。誤って基盤自身へ`.ai-dev`を作らないよう、アプリケーションは本リポジトリの外に置く。

## ホストの初回設定

各サービスの個人向け有料契約によるOAuthログインを使用する。APIキーはリポジトリにもオーケストレーション環境にも追加しない。

拡張チャットへ次のように依頼する。

> Triadを使うためのCodex、Claude Code、Antigravity、Git、Dockerの状態を確認して。ログインが必要なら進めて。

チャット担当AIが環境診断とログイン開始を行う。ブラウザにOAuth確認画面が出た場合の同意や、Antigravityが表示する認証コードの入力だけは人間が行う。Antigravityには副作用なしで認証状態だけを確認するサブコマンドがないため、初回利用時に確認する。

## 新しいアプリケーションの開始

チャットへ作成先、プロジェクト名、作りたいものを伝える。タスクIDや主力実装AIを指定しなければ、チャット担当AIが既定値または合理的な値を選ぶ。

> `~/workspace`に`todo-app`を作って。「スマートフォンで日々のタスクを簡単に管理したい」を最初の依頼にして、Triadで進めて。

チャット担当AIは`triad-new`を非対話で実行する。新しいGitリポジトリ、README、`.gitignore`、チャット用AI指示、`.ai-dev`、人間の短い依頼、初回コミットを準備し、Codexに解決方法を確定しない調査・協議ブリーフを作成させる。既存のファイルまたはディレクトリは上書きしない。Gitの`user.name`と`user.email`が未設定なら、必要な値を人間へ尋ねる。

ブリーフ作成後も人間の承認では停止しない。チャット担当AIは次の協議を順に進める。

1. Antigravityが公式情報、競合、現行仕様、技術制約を調査する。
2. Claudeが要求・制約を分析し、複数の実現案と推奨案を作る。
3. Codexが依頼と調査から独立見解を組み立て、Claude案の見落としと代替案をレビューする。
4. Antigravityが両者の外部事実と現行仕様を再確認する。
5. Codexが候補比較、採用する方針、採否理由、仮定、リスクを決定する。
6. Claudeが統合方針の正確性、公平性、実現可能性を独立レビューする。
7. Claudeが検証可能な要件を定義し、Codexが独立レビューする。
8. Claudeがアーキテクチャ・API・データ・運用・テストを設計し、Antigravityが外部前提を実地確認し、Codexが独立レビューする。
9. Codexが統合方針・要件・設計・各レビュー判定・リスク・仮定を1件の計画書へまとめ、Claudeが最終レビューする。

すべて揃うと状態は`AWAITING_PLAN_APPROVAL`になる。チャット担当AIは計画書に加え、比較した候補、各AIの主な見解、レビュー結果、Antigravityをスキップした場合の不足を提示して停止する。人間はその後のメッセージで「承認」または具体的な修正理由を返す。

## 既存アプリケーションでのタスク開始

対象は既存のGitリポジトリでなければならない。チャットへ対象パスと短い依頼を伝える。

> `/path/to/app`にTriadを導入して。「期限切れタスクを一覧で目立たせたい」を`APP-001`として進めて。

初回タスクの初期化では、採用済みの知識基準と成果物テンプレートを`.ai-dev/guidance/`へ複製し、`manifest.json`にSHA-256を記録する。また、既存の`AGENTS.md`・`CLAUDE.md`・`GEMINI.md`を上書きせず、Triadチャット操作規約への短い案内を一度だけ追記する。チャット担当AIは初期化結果を確認してローカルコミットし、3AIの調査・協議へ進む。

同じリポジトリの後続タスクでは固定済みガイダンスを検証するだけで、基盤側の新しい知識へ自動更新しない。新しい知識版の採用は、影響をレビューする独立した変更要求として扱う。

## 日常の進行

人間は「続きを進めて」「現在の状況を教えて」「この不具合を新しいタスクとして直して」のように依頼する。チャット担当AIは次のサイクルを内部で繰り返す。

1. 状態、担当、期待される成果物、未解決の判断を確認する。
2. 現在フェーズの担当AIまたはDocker Compose検証を実行する。
3. 成果物とレビュー判定を検証し、対応する状態遷移を進める。
4. 必要なローカルコミットを作成する。
5. 計画または成果物完成の承認が必要になるか、後続工程で回答・追加権限が必要になるか、エラーで安全に継続できなくなるまで繰り返す。

レビューフェーズでは、レビュー文書のフロントマターに保存された判定と一致する結果だけを使用する。調査とE2Eのスキップは、担当機能を利用できない場合に限り、具体的な理由を履歴へ残す。

## 人間による承認ゲート

Triadは`AWAITING_PLAN_APPROVAL`（計画承認）と`AWAITING_DELIVERY_APPROVAL`（成果物完成確認）の2箇所でだけ人間を止める。いずれも次の二段階を必須とする。

1. チャット担当AIが対象成果物、重要な変更、対象ハッシュ、承認の影響を提示して停止する。
2. その提示より後の人間メッセージが「承認」「この内容で進めて」など対象操作を明示した場合だけ、チャット担当AIが確認句をCLIへ中継する。

作業開始時の「完成まで進めて」「全部任せる」のような包括的な依頼は、まだ提示されていない成果物の承認として扱わない。沈黙、曖昧な返答、AI自身の判断も承認ではない。人間は確認句やコマンドを転記する必要がない。

確認句は対象パスとSHA-256に結び付く。提示後に対象が変化した場合、古い確認句では操作できない。承認記録には対象ファイルのSHA-256と`confirmation_channel: vscode-chat`を保存する。承認後、チャット担当AIは記録と新しい状態をローカルコミットして通常フェーズへ戻る。

チャット確認句は秘密ではなく、CLI単体では人間の発言を証明しない。チャット担当AIがリポジトリの二段階確認規約を守ることを信頼する、単一ユーザーのローカル運用向け経路である。プロンプトインジェクションや侵害されたチャット担当からも承認を保護する必要があると人間が示した場合は、チャットで承認を中継せず、対話端末による直接確認が必要だと伝える。

## 計画の差し戻しと成果物の作り直し

**計画承認**（`AWAITING_PLAN_APPROVAL`）に問題があれば、提示後に修正理由をそのまま返信する。

> 対象利用者を個人に絞って。デスクトップよりスマートフォンを優先して作り直して。

チャット担当AIは明示された理由、確認経路、提示した計画書一式のハッシュをGitへ記録し、状態を`INTAKE`へ戻す。3AIは修正理由を新しい入力として調査・提案・要件・設計・計画をやり直す。

**成果物完成確認**（`AWAITING_DELIVERY_APPROVAL`）で完成した成果物に問題があれば、同様に理由を返信する。

> ボタンが小さすぎて押しにくい。もう少し大きくして。

この場合はチャット担当AIが状態を`FIX`へ戻す。承認済み計画自体は変更せず、その範囲内での実装のみをやり直す軽量な差し戻しである。修正後は`CODE_REVIEW`・`BUILD_TEST`・`E2E_VERIFY`・`DELIVERY_PREP`・`DELIVERY_REVIEW`を経て、再び`AWAITING_DELIVERY_APPROVAL`で人間に確認する。

単なる質問や感想を差し戻し・作り直しとして処理しない。

## AIからの判断依頼

AIが重要な質問を提示した場合、通常の状態遷移は停止する。チャット担当AIは質問、選択肢、推奨案、影響を提示する。人間がすべての質問へ自然言語で回答した後、回答付きの`status`で回答内容にも束縛された確認句を取得し、その回答と確認経路を判断記録へ保存する。別の回答へ差し替えると確認句が一致しない。

回答数が不足している場合や解釈が複数ある場合だけ追加質問する。質問を発生させた成果物のハッシュと回答はGit上で結び付ける。計画マクロフェーズ（`INTAKE`〜`PLAN_REVIEW`）では、この仕組みは使わない——不足情報は仮定・選択肢・リスクとして成果物本文へ明示し、計画承認の1回でまとめて人間の判断を仰ぐ。

## 承認済み計画との矛盾

計画承認後（`TASK_BREAKDOWN`以降`DELIVERED`未満）、AIは承認済み計画を変更せず、変更要求を作成して停止する。承認されると計画承認を無効化し、`INTAKE`から3AIの調査・提案・要件・設計・計画をやり直す。計画承認前の問題（3AIの協議中や計画提示直後に生じた問題）は、より軽量な計画差し戻し（`advance --outcome needs_changes`）で扱うため、変更要求の対象にしない。

チャット担当AIは変更理由と影響を人間へ提示する。提示後の別メッセージで人間が明示的に承認した場合だけ、承認を無効化して再開する。

## 同時操作について

同一タスクへの`advance`・`approve`・`request-change`・`approve-change`・`decide`、およびAI実行・ビルド検証は、タスク単位のロックで直列化される。複数のチャット窓口を同時に開いて同じタスクを操作した場合、片方は最大10秒待った上で明確なエラーになる（無言で競合したり、片方の変更が消えたりはしない）。エラーになった側は少し待って再試行する。

## コミットメッセージ

成果物を作るAI子プロセスは`git commit`を実行しない。VS Codeのチャット担当AIはオーケストレーターとして、検証済みの変更と状態記録をローカルコミットできる。実際のGit authorとは別に、変更内容を作成した担当をtrailerへ記録する。

```text
feat(todo): タスクの追加と完了切り替えを実装

Triad-Task: APP-001
Produced-By: claude
Reviewed-By: codex
```

件名はConventional Commitsのtypeを英語で維持し、要約を日本語にする。主なtypeは`feat`、`fix`、`docs`、`test`、`refactor`、`chore`、`build`とする。`.ai-dev`だけの変更は原則として`docs(ai-dev)`を使用する。`Reviewed-By`は独立レビュー完了後のコミットにだけ記録する。

## チャット担当AIが使うCLI

CLIはVS Codeチャットの内部実行面であり、人間向けUIではない。

| 目的 | CLI操作 |
|---|---|
| 環境診断 | `triad doctor` |
| タスク作成 | `triad init` |
| 状態と確認句の取得 | `triad status`（判断回答時は`--answer`を質問順に指定） |
| 担当フェーズの実行 | `triad run` |
| 通常の状態遷移 | `triad advance` |
| 明示された承認の中継 | `triad approve <task_id> plan\|delivery --human-confirmation ...` |
| 明示された計画の差し戻し・成果物の作り直しの中継 | `triad advance --outcome needs_changes --human-confirmation ...` |
| 明示された判断回答の中継 | `triad decide --human-confirmation ...` |
| 承認済み計画の変更提案と承認 | `triad request-change` / `triad approve-change --human-confirmation ...` |

`status`は人間操作が可能な状態で、対象ハッシュとハッシュ拘束された確認句を`human_actions`へ返す。チャット担当AIはそこに含まれる確認句を、人間の明示意思がある場合にだけ使用する。`TRIAD_AGENT_RUN=1`のAI子プロセスから承認・差し戻し・判断回答を行うことはできない。

## 各アプリケーションのDocker契約

生成される`.ai-dev/project.json`では、ビルド・テストコマンドの既定値を次のように設定する。

```json
{"compose": {"build_test": ["docker", "compose", "run", "--rm", "test"]}}
```

引数一覧はアプリケーションのComposeサービスに合わせて変更できるが、実行入口は`docker compose`だけにする。アプリケーション言語のパッケージ管理ツールはイメージ内へ配置し、WSLホストには置かない。

自動テストは安全なComposeモデルだけを受け付ける。ホスト外部へのバインド・ビルドパス、Dockerソケット、特権設定、ホスト名前空間、デバイス、追加ケイパビリティ、制限なしのセキュリティ設定、外部の`include`・`extends`・`env_file`参照は拒否する。`compose.override.yaml`等のオーバーライドファイルがメインのComposeファイルと併存する場合も自動テストを拒否する。本当に必要な場合は、人間がレビューするインフラ変更として提示し、自動テスト経路の外で扱う。

## 禁止操作

本基盤はpush、マージ、本番デプロイ、本番マイグレーション、破壊的なDB操作、force push、履歴書き換えを行わない。`DELIVERED`は、人間が判断するための資料が準備できたことだけを意味する。VS Codeチャットから依頼されても、これらを成果物完成確認の延長として実行してはならない。
